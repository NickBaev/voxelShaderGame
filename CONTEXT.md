# Контекст проекта: воксельный движок и изометрическая action RPG

## 1. Суть проекта

Пользователь планирует самостоятельно создать игру и простой собственный движок для неё.

**Игра:**

- изометрическая / top-down action RPG;
- процедурно генерируемый воксельный мир;
- сильный упор на разрушаемость;
- частицы и физика твёрдых тел;
- перегенерация и перестроение чанков налётчу;
- визуально и технически это не просто Minecraft-клон: разрушение должно быть частью игрового процесса.

Изометрический вид предполагается реализовать прежде всего через ортографическую камеру, а не через отдельный тип движка.

## 2. Что пользователь хочет изучить

Проект одновременно является учебным. Цель — **глубоко разобраться во внутреннем устройстве**, а не просто собрать игру на готовых компонентах:

- графический pipeline;
- шейдеры;
- compute shaders;
- архитектура GPU;
- память GPU, кэши, workgroups, barriers, atomics, occupancy и divergence;
- синхронизация CPU–GPU;
- процедурная генерация;
- воксельные алгоритмы;
- meshing и voxel ray traversal;
- collision detection и физика твёрдых тел;
- профилирование и отладка GPU.

Пользователь уже прошёл **tiny renderer**, поэтому имеет базовое представление о программной растеризации. **Compute shaders пока не писал.**

Vulkan рассматривался как подходящий API для глубокого изучения из-за явного управления памятью, командами и синхронизацией. Конкретные Go bindings, windowing library и детали платформы пока не выбраны.

## 3. Как помогать пользователю

- Пользователь хочет **писать код самостоятельно**.
- Не выдавать полные реализации без явной просьбы.
- Можно давать архитектуру, пошаговый план, математику, псевдокод, небольшие сигнатуры или болванки кода.
- Объяснять причины решений, компромиссы и возможные ошибки.
- Предлагать тесты и критерии корректности.
- При ошибке или изменении решения явно корректировать предыдущий совет.
- Не превращать работу в создание универсального движка раньше времени: каждый этап должен заканчиваться проверяемым результатом.
- Основной язык общения — русский.

## 4. Целевая архитектура

Архитектура амбициозна намеренно: пользователь хочет исследовать GPU-подход. При этом GPU не является догмой; для отладки допустимы небольшие CPU-reference и аналитические тесты.

### Go — тонкий CPU-клиент

Предполагаемые обязанности:

- окно и ввод;
- камера;
- основная игровая логика;
- характеристики, инвентарь, квесты;
- высокоуровневый ИИ;
- запросы на загрузку, выгрузку и перестроение чанков;
- сохранения;
- обработка компактных игровых событий, полученных с GPU.

Go не должен хранить полную копию активного воксельного мира «на всякий случай».

### GPU

Постепенно планируется перенести на GPU:

- хранение активных чанков;
- процедурную генерацию вокселей;
- построение и перестроение мешей;
- culling и indirect draw;
- рендеринг;
- частицы;
- физику твёрдых тел;
- игровые ray queries и события столкновений, если это окажется практичным.

### Диск и сохранения

Мир нельзя восстанавливать только из seed, если игрок может его разрушать. Модель сохранения:

> seed → детерминированная базовая генерация → применение сохранённых изменений → построение видимой поверхности и физических данных.

На диске предполагается хранить:

- seed мира;
- компактный журнал изменений вокселей;
- состояние важных игровых сущностей.

### Связь Go и GPU

- Компактные command/event buffers.
- Не читать полные чанки обратно на CPU.
- Не выполнять синхронный readback мира каждый кадр.
- Игровые события с GPU читать небольшими порциями и, где возможно, асинхронно.
- CPU может знать координаты чанка, состояние и GPU slot, но не всё содержимое чанка.
- Readback допустим как отладочный и тестовый инструмент.

## 5. Главный текущий эксперимент: GPU meshing против voxel DDA

Окончательный способ рендеринга воксельного мира **ещё не выбран**. Нужно построить два пути поверх одного и того же GPU voxel buffer и сравнить их.

### Вариант A: GPU mesher + растеризация

Конечный мешер должен работать на GPU. Полноценный production CPU-мешер не нужен.

Первый вариант алгоритма:

1. Один compute invocation на воксель.
2. Для непустого вокселя проверить шесть соседей.
3. Создать грань, если соответствующий сосед пуст.
4. Использовать атомарный счётчик и заранее выделенный консервативный output buffer.
5. Передать результат в raster pipeline через indirect draw без обычного readback.

Сначала реализуется наивный visible-face meshing. **Greedy meshing отложен** до появления корректного baseline.

Последующие оптимизации, только если они понадобятся:

- count pass;
- prefix sum;
- compaction;
- более экономное управление выходной памятью;
- уменьшение влияния atomics;
- GPU greedy meshing.

В Vulkan особое внимание уделить:

- сбросу счётчиков;
- dependencies между compute и vertex/indirect стадиями;
- memory barriers;
- frames in flight;
- запрету переиспользования ресурсов, которые ещё читает GPU;
- **память буферов: voxel/mesh SSBO должны быть device-local; host-visible staging-буферы — отдельно для upload (CPU→GPU) и readback (GPU→CPU), перенос через `vkCmdCopyBuffer`. Один host-visible буфер в Этапе 2 — осознанное упрощение прототипа, заменить до замеров производительности (см. обсуждение PCIe vs GDDR).**
- **staging-буферам вместо map/unmap на каждую операцию перейти на персистентный mapping (один map на всю жизнь буфера) — когда появится staging-поток в Этапе 3.**

### Вариант B: compute voxel DDA

Для кубического воксельного мира выбран **DDA**, а не ray marching с фиксированным шагом и не sphere tracing по SDF.

Базовый план:

1. Compute shader запускает один луч на пиксель.
2. Луч проходит непосредственно по voxel buffer.
3. Для первого попадания определяются position, normal, material ID, voxel coordinate и distance.
4. Первый прототип может сразу записывать цвет в storage image.
5. Позже возможен G-buffer-подобный вариант с отдельным lighting pass.

Для ортографической камеры:

- `rayDirection` одинаков для всех пикселей;
- `rayOrigin` изменяется по плоскости камеры.

Нужно отдельно обработать:

- нулевые компоненты направления;
- начало луча внутри твёрдого вокселя;
- отрицательные направления;
- выход за пределы чанка;
- лучи вдоль граней и рёбер;
- ограничение числа шагов;
- пересечение луча с AABB чанка, чтобы не проходить пустое пространство от камеры.

Динамические mesh-объекты, персонажи, обломки и частицы при любом варианте первоначально разумно растеризовать. Полностью «чистый» ray-marched renderer всей игры не является обязательной целью.

### Что DDA не решает

DDA не заменяет:

- collision detection;
- physics solver;
- уведомление физики об изменениях мира;
- streaming;
- acceleration structures для нескольких чанков;
- сохранение разрушений.

### Условия честного сравнения

Оба пути должны использовать:

- один voxel buffer;
- одну камеру;
- одинаковое разрешение;
- одинаковые материалы и освещение;
- одинаковые тестовые сцены.

Сначала добиться визуального совпадения, затем измерять производительность.

Метрики:

- GPU frame time;
- время построения / перестроения меша;
- количество граней, вершин и треугольников;
- память voxel и mesh buffers;
- среднее и максимальное число шагов DDA;
- масштабирование по разрешению;
- масштабирование по дальности обзора;
- поведение на пустом и плотном мире;
- задержка обновления после изменения одного вокселя.

## 6. Ограничения первого прототипа

Пока не добавлять бесконечный мир, streaming, биомы, физику и разрушения.

Фиксированные условия:

- один чанк `32 × 32 × 32`;
- один material ID на воксель;
- `Air = 0`, остальные значения — твёрдые материалы;
- для простоты первого SSBO material хранится как `uint32`, а не `uint8`;
- локальные координаты `0…31`;
- воксель `(x,y,z)` занимает `[x,x+1) × [y,y+1) × [z,z+1)`;
- порядок хранения: `x + ChunkSize * (y + ChunkSize * z)`;
- при работе с одиночным чанком всё за его пределами считается воздухом;
- ортографическая камера;
- один направленный источник света;
- только непрозрачные воксели.

При переходе к нескольким чанкам правило «за пределами воздух» будет заменено neighbor lookup или halo.

## 7. Текущий практический этап

Согласовано начать с **генераторов тестовых чанков на Go**. Ранее обсуждался возможный код, но в этот handoff он намеренно не переносится: пользователь напишет реализацию сам.

Нужны следующие генераторы:

1. Пустой чанк.
2. Полностью заполненный чанк.
3. Один воксель в центре.
4. Два соседних вокселя с общей внутренней гранью.
5. Горизонтальная плоскость толщиной один воксель.
6. Воксельная сфера.
7. Шахматный узор.
8. Детерминированный шум с фиксированным seed и настраиваемой плотностью.

Базовые операции:

- выделение хранилища;
- bounds check;
- index calculation;
- `Get`;
- `Set`;
- `Fill`;
- подсчёт статистики для тестов.

Для сферы учитывать центр вокселя `(x+0.5, y+0.5, z+0.5)`, чтобы форма была симметричной относительно центра чанка.

## 8. Проверки без полноценного CPU-мешера

Достаточно CPU-статистики и аналитических тестов. Статистика не должна стать частью production pipeline.

Ожидаемые значения visible-face meshing:

- пустой чанк: `0` граней;
- одиночный воксель: `6` граней, `12` треугольников;
- два соседних вокселя: `10` граней, `20` треугольников;
- полный чанк `32³`, если снаружи воздух: `6 × 32² = 6144` грани, `12288` треугольников;
- плоскость `32 × 32 × 1`: `2 × 32² + 4 × 32 = 2176` граней.

Дополнительно проверить:

- отрицательные и выходящие за границы координаты;
- воксели на всех внешних границах;
- углы чанка;
- нормали и winding;
- повторяемость шума при одинаковом seed;
- отсутствие общих граней у твёрдых вокселей шахматного узора.

## 9. Ближайшая последовательность работ

### Этап 1 — Go voxel core

- Реализовать соглашения хранения.
- Реализовать генераторы.
- Реализовать статистику и аналитические тесты.
- Не добавлять world coordinates и streaming.

### Этап 2 — минимальное знакомство с compute

Так как compute shaders ещё не изучены, не начинать сразу с полного мешера:

- загрузить один тестовый чанк в GPU storage buffer;
- написать простой compute shader;
- повторить подсчёт `SolidVoxels` и `VisibleFaces`;
- вернуть только небольшие счётчики в тестовом режиме;
- сравнить результаты с Go.

При необходимости перед этим отдельно сделать минимальный Vulkan compute example, который просто пишет в storage buffer или storage image.

### Этап 3 — GPU mesher

- Наивный one-invocation-per-voxel mesher.
- Atomics и консервативный buffer.
- Indirect draw.
- Проверка аналитических сцен.
- Никакой преждевременной оптимизации.
- Перед замерами: перейти на device-local буферы + staging (см. раздел 5).

### Этап 4 — DDA

- Сначала при необходимости CPU-reference для понимания алгоритма.
- Затем compute DDA по тому же buffer.
- Режимы вывода normals, material ID, depth и числа шагов.

### Этап 5 — сравнение

- Визуальное совпадение.
- GPU timestamps.
- Таблица результатов по тестовым сценам.
- Только после этого выбрать основной путь или гибрид.

## 10. Последующая архитектура после эксперимента

Эти системы пока не реализовывать, но решения зафиксированы как направление.

### Chunk lifecycle

Пример состояний:

`Requested → Allocated → Generating → ApplyingEdits → Meshing → Ready → Evicting`

Для DDA этап Meshing заменяется подготовкой traversal-данных.

Нужны:

- версии асинхронных заданий;
- защита от записи результата старой работы в новый slot;
- free list GPU slots;
- memory budget;
- ограничение работ за кадр;
- приоритеты по расстоянию;
- корректная выгрузка ресурсов, ещё используемых GPU;
- dirty flags для соседних чанков при изменении границы.

### Физика

Изучать постепенно:

1. fixed timestep;
2. semi-implicit Euler;
3. простые формы;
4. collision detection;
5. contacts;
6. sequential impulse solver;
7. friction и restitution;
8. вращение, quaternions и inertia tensor;
9. sleeping;
10. broadphase;
11. взаимодействие с изменяемым воксельным миром.

Небольшой CPU-reference допустим для обучения и проверки, даже если конечная симуляция будет на GPU.

### Разрушение

Разделить на уровни:

1. изменение вокселей и обновление представления мира;
2. большое количество визуальных GPU-частиц;
3. ограниченное число полноценных rigid-body обломков;
4. позже — связность, обрушения и более сложные разрушения.

Для обломков предусмотреть лимиты, pooling, sleeping и время жизни. Runtime fracture произвольной геометрии отложен.

## 11. Что намеренно отложено

- бесконечный streaming;
- сложные биомы;
- GPU greedy meshing;
- идеальный GPU allocator;
- prefix sum / compaction до появления baseline;
- несколько чанков и halo;
- async compute;
- bindless;
- сложный deferred renderer;
- voxel GI и ray tracing;
- произвольный runtime fracture;
- детерминированный GPU physics solver;
- универсальный ECS и чрезмерные абстракции движка.

## 12. Полезные материалы

- Amanatides & Woo — **“A Fast Voxel Traversal Algorithm for Ray Tracing”**.
- 0fps — **“Meshing in a Minecraft Game”**.
- Vulkan Tutorial, Vulkan Specification, Khronos Vulkan Samples.
- **Real-Time Rendering**.
- **Programming Massively Parallel Processors**.
- Christer Ericson — **Real-Time Collision Detection**.
- Материалы Erin Catto и исходники Box2D / Bullet для последующего изучения физики.

## 13. Незакрытые решения

Не считать уже выбранными:

- окончательный renderer: meshing, DDA или гибрид;
- конкретные Vulkan bindings для Go;
- windowing library;
- формат GPU mesh buffer;
- способ интеграции динамических mesh-объектов с DDA depth;
- acceleration structure для нескольких чанков;
- конкретную GPU physics architecture.

## 14. Как продолжить работу

Начать с текущего этапа: помочь пользователю самостоятельно реализовать Go voxel core и генераторы тестовых чанков.

Предпочтительный формат помощи:

1. кратко восстановить соглашения;
2. предложить структуру пакета и сигнатуры функций;
3. дать список тестов;
4. указать на типичные ошибки;
5. не писать полную реализацию, пока пользователь явно её не попросит.

После этого перейти к первому minimal compute shader, который считает непустые воксели и видимые грани на GPU и сверяется с Go-статистикой.
